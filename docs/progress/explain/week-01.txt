# Explain-Back Minggu 01 — Perjalanan Request Web

Pada Minggu 1 saya mempelajari apa yang sebenarnya terjadi ketika client mengakses sebuah website melalui HTTPS. Fokus saya bukan hanya menghafal DNS, TCP, TLS, dan HTTP sebagai istilah terpisah, tetapi memahami bagaimana semuanya bekerja sebagai rangkaian proses dari sebuah nama domain sampai response diterima dan halaman dapat ditampilkan.

Ketika saya mengakses URL seperti `https://github.com`, client terlebih dahulu membutuhkan alamat IP dari domain `github.com`. Proses ini dilakukan melalui DNS resolution. Sebelum melakukan pencarian ke jaringan, hasil DNS dapat ditemukan lebih dulu dari cache browser, cache sistem operasi, atau cache DNS resolver. Jika belum tersedia, resolver dapat melakukan pencarian melalui root DNS server, TLD server untuk `.com`, lalu authoritative DNS server yang mengetahui record untuk `github.com`. Hasil DNS memiliki TTL atau Time To Live yang menentukan berapa lama informasi tersebut boleh disimpan di cache sebelum perlu diperbarui.

Pada percobaan menggunakan `curl -v https://github.com`, saya dapat melihat bahwa `github.com` berhasil di-resolve menjadi sebuah alamat IPv4 dan kemudian curl mencoba terhubung ke alamat tersebut pada port `443`. Output `curl -v` hanya menunjukkan hasil akhir resolusi DNS, bukan seluruh komunikasi antara resolver, root, TLD, dan authoritative server. Karena adanya caching, rangkaian lookup DNS tersebut juga tidak selalu dilakukan secara lengkap untuk setiap request.

Setelah alamat IP diketahui, client perlu membuat koneksi dengan server. Untuk HTTPS berbasis TCP, koneksi biasanya dilakukan ke port `443`. TCP membentuk koneksi menggunakan three-way handshake yang terdiri dari `SYN`, `SYN-ACK`, dan `ACK`. Client mengirim SYN, server membalas SYN-ACK, kemudian client mengirim ACK. Setelah proses ini selesai, koneksi TCP terbentuk. `curl -v` menunjukkan proses koneksi ke alamat IP dan port 443, tetapi tidak memperlihatkan paket SYN, SYN-ACK, dan ACK secara langsung. Untuk melihat paket tersebut secara eksplisit diperlukan tool yang bekerja pada level jaringan seperti `tcpdump` atau Wireshark.

Setelah koneksi TCP tersedia, HTTPS membutuhkan TLS untuk membuat komunikasi yang aman. Dari output `curl -v`, saya dapat melihat TLS 1.3 handshake dimulai dengan `Client hello`, kemudian server membalas dengan `Server hello`. Dalam proses ini client dan server menegosiasikan parameter kriptografi yang akan digunakan. Curl juga menawarkan protokol aplikasi melalui ALPN, pada percobaan ini berupa HTTP/2 atau HTTP/1.1.

Server kemudian mengirimkan certificate yang digunakan client untuk memverifikasi identitas server. Sertifikat tersebut tidak dipercaya hanya karena dikirim oleh server, tetapi diverifikasi melalui certificate chain hingga mencapai Certificate Authority atau CA yang sudah dipercaya oleh sistem. Pada Linux saya, curl menunjukkan trust anchor yang berasal dari `/etc/ssl/certs/ca-certificates.crt`. Dengan mekanisme ini client dapat memeriksa bahwa sertifikat yang diterima memang valid untuk server yang sedang dihubungi dan memiliki rantai kepercayaan yang dapat diverifikasi.

Setelah certificate verification dan bagian akhir TLS handshake berhasil, client dan server memiliki material kriptografi yang diperlukan untuk membentuk session key. Session key inilah yang kemudian digunakan untuk mengenkripsi komunikasi selama koneksi berlangsung. Jadi TLS tidak hanya bertujuan menyembunyikan isi komunikasi, tetapi juga membantu memastikan identitas pihak yang dihubungi dan menjaga integritas data selama perjalanan.

Setelah koneksi TLS siap, barulah HTTP request dapat dikirim melalui kanal tersebut. Request mempunyai method seperti `GET` atau `POST`, path seperti `/`, dan sejumlah header termasuk informasi host yang ingin diakses. Secara konseptual ketika membuka halaman utama GitHub, client dapat mengirim request seperti `GET /` untuk meminta resource pada root path `github.com`. Pada percobaan awal saya menggunakan `head -30`, sehingga output berhenti pada bagian TLS handshake dan bagian HTTP request belum terlihat. Ini menunjukkan bahwa penggunaan tool observasi juga harus dipahami dengan benar; tidak munculnya HTTP request pada output tersebut bukan berarti HTTP request tidak pernah dilakukan, tetapi karena output sengaja dipotong.

Di sisi server, request yang masuk tidak selalu langsung ditangani oleh satu aplikasi. Dalam arsitektur web, request dapat terlebih dahulu melewati reverse proxy atau load balancer sebelum diteruskan ke aplikasi. Aplikasi kemudian menjalankan business logic dan, jika diperlukan, berkomunikasi dengan database, cache, atau service lain. Setelah proses selesai, server membentuk HTTP response dan mengirimkannya kembali kepada client. Detail implementasi internal seperti reverse proxy, aplikasi, atau database ini tidak dapat diketahui secara lengkap hanya dari `curl`, karena dari sudut pandang client yang terlihat terutama adalah interface jaringan dan response yang dikembalikan server.

HTTP response memiliki status code, headers, dan dapat membawa body seperti HTML. Status code memberikan informasi mengenai hasil request, misalnya kelompok `2xx` untuk keberhasilan, `3xx` untuk redirect, `4xx` untuk kesalahan dari sisi request client, dan `5xx` untuk masalah di sisi server. Curl dapat digunakan untuk melihat response tersebut, tetapi curl tidak berperilaku seperti browser dalam merender halaman.

Ketika browser menerima HTML, pekerjaannya belum selesai. Browser mem-parsing HTML dan menemukan resource turunan seperti CSS, JavaScript, gambar, font, atau resource lainnya. Browser kemudian dapat membuat request HTTP tambahan untuk mengambil resource-resource tersebut. Setelah resource yang diperlukan tersedia, browser melakukan proses seperti membangun struktur halaman, menghitung layout, dan menggambar hasilnya ke layar. Karena itu, membuka satu URL di browser biasanya dapat menghasilkan banyak request jaringan dan bukan hanya satu request untuk dokumen HTML utama.

Dari latihan `curl -v`, saya memahami bahwa DNS, TCP, TLS, dan HTTP bukan empat proses yang berdiri sendiri. DNS digunakan untuk menemukan tujuan jaringan. TCP membentuk koneksi transport ke server. TLS berjalan di atas koneksi tersebut untuk membangun komunikasi yang terenkripsi dan terautentikasi. HTTP kemudian menggunakan kanal tersebut untuk mengirim request dan menerima response. Setelah response diterima, browser masih memiliki tanggung jawab untuk mengambil resource tambahan dan melakukan rendering.

Saya juga memahami batas dari tool yang digunakan. `curl -v` dapat menunjukkan hasil DNS resolution, tujuan IP dan port, TLS handshake, certificate, HTTP request, dan HTTP response, tetapi tidak menunjukkan seluruh mekanisme DNS resolution, paket TCP handshake secara detail, implementasi internal server, maupun proses rendering browser. Untuk mengamati bagian yang berbeda diperlukan tool yang berbeda, misalnya `dig` untuk DNS, `tcpdump` atau Wireshark untuk packet-level networking, `curl` untuk HTTP dan TLS dari sisi client, serta browser DevTools untuk request resource dan proses browser.

Kesimpulan saya dari Minggu 1 adalah bahwa mengakses sebuah website merupakan rangkaian beberapa layer yang saling bergantung. Sebelum HTTP dapat berjalan, client harus mengetahui tujuan melalui DNS, membangun koneksi transport, lalu menyiapkan keamanan TLS. Request kemudian diproses oleh server dan response akhirnya digunakan browser untuk membangun halaman. Tujuan latihan ini bukan sekadar membuat saya hafal urutan `DNS → TCP → TLS → HTTP → server → render`, tetapi membuat saya mampu menjelaskan fungsi setiap tahap, hubungan antar-tahap, dan bagian mana yang benar-benar dapat saya buktikan melalui evidence dari tool yang saya jalankan.
