# Explain-Back Minggu 02 — Docker & Compose sampai ke Tulang

Pada Minggu 2 saya mempelajari bagaimana aplikasi API Go dikemas ke dalam container Docker yang kecil dan aman, kemudian dijalankan bersama dependency seperti PostgreSQL dan Redis menggunakan Docker Compose. Fokus saya bukan hanya membuat `docker build` atau `docker compose up` berhasil, tetapi memahami bagaimana build image, runtime container, healthcheck, networking, volume, resource limit, dan development environment saling berhubungan serta bagaimana setiap klaim tersebut dapat dibuktikan melalui evidence yang sesuai.

Pada bagian Dockerfile, saya menggunakan pendekatan multi-stage build. Stage build membawa toolchain Go yang dibutuhkan untuk mengompilasi aplikasi, sedangkan stage runtime hanya membawa binary hasil build dan komponen yang benar-benar diperlukan ketika aplikasi dijalankan. Dengan pemisahan ini, compiler, source code, dan tool development tidak perlu ikut berada di image produksi. Runtime akhirnya menggunakan `gcr.io/distroless/static-debian12:nonroot`, sehingga image produksi dapat dibuat jauh lebih kecil dan secara default tidak berjalan sebagai root. Image API terakhir yang saya ukur berukuran sekitar 14.6MB dan user efektifnya adalah UID `65532`.

Pada proses build Go, Dockerfile menyalin `go.mod` dan `go.sum*` lebih dahulu lalu menjalankan `go mod download` sebelum melakukan `COPY . ./`. Tujuannya adalah memanfaatkan layer cache Docker. Dependency Go biasanya berubah lebih jarang dibanding source application. Karena itu, ketika hanya source code yang berubah, layer hasil download dependency masih dapat digunakan kembali dan Docker tidak perlu mengunduh dependency dari awal. Penggunaan `go.sum*` juga disengaja. Pada kondisi project belum mempunyai dependency, file `go.sum` belum tentu ada. Jika Dockerfile menggunakan `COPY go.mod go.sum ./`, build akan gagal ketika `go.sum` tidak tersedia, sedangkan wildcard membuat file tersebut bersifat opsional.

Saya juga mempelajari bahwa `.dockerignore` memengaruhi build context yang dikirim ke builder, bukan secara langsung ukuran akhir image. Setelah `.dockerignore` dibatasi menggunakan whitelist, ukuran transfer build context yang diukur berubah dari 942B menjadi 621B, atau turun sekitar 34,1%. Dari percobaan ini saya memahami bahwa alat ukur harus sesuai dengan objek yang ingin dibuktikan. Membandingkan ukuran image sebelum dan sesudah `.dockerignore` tidak cukup untuk membuktikan bahwa build context mengecil. Evidence yang benar justru berasal dari output build pada bagian transfer context.

Runtime distroless memberikan keuntungan karena sangat minimal, tetapi sifat minimal tersebut juga mempunyai konsekuensi. Image distroless tidak menyediakan shell maupun HTTP client seperti `wget` yang biasanya dapat digunakan untuk Docker `HEALTHCHECK`. Solusi awal yang sempat digunakan adalah menambahkan BusyBox agar tersedia executable untuk melakukan HTTP probe. Namun setelah diukur, BusyBox menambah layer sekitar 1.22MB. Image dengan pendekatan tersebut tercatat sekitar 15.9MB, sedangkan runtime akhir tanpa BusyBox sekitar 14.6MB.

Karena itu, solusi akhirnya adalah menggunakan binary API sendiri sebagai healthcheck melalui `HEALTHCHECK CMD ["/api", "-healthcheck"]`. Ketika flag `-healthcheck` aktif, `main` membangun alamat lokal `http://127.0.0.1:<port>/healthz` kemudian memanggil `healthcheck.Probe` yang berada di `apps/api/internal/healthcheck/probe.go`. Probe tersebut membuat HTTP request menggunakan context, memiliki timeout dua detik, dan hanya menganggap HTTP status `200` sebagai kondisi sehat. Jika endpoint mengembalikan status seperti `503` atau request melewati timeout, probe menghasilkan error sehingga mode healthcheck keluar sebagai gagal.

Dari implementasi ini saya memahami bahwa Docker `HEALTHCHECK` bukan mekanisme khusus yang secara otomatis mengetahui kondisi aplikasi. Docker pada dasarnya menjalankan command yang didefinisikan secara berkala dan menggunakan exit status command tersebut untuk menentukan apakah container sehat atau tidak. Pada runtime distroless, command itu harus benar-benar tersedia di filesystem image. Dengan menggunakan `/api -healthcheck`, saya tidak perlu menambahkan shell atau HTTP client hanya untuk menjalankan probe.

Keputusan memakai distroless juga mempunyai trade-off. Image yang minimal mengurangi komponen yang dibawa ke production dan membuat ukuran runtime kecil, tetapi debugging di dalam container menjadi lebih sulit karena tidak tersedia shell dan utility umum. Konsekuensi ini diterima dan dicatat pada ADR-0005. Jika debugging runtime diperlukan, pendekatannya bukan mengandalkan shell yang selalu tersedia di image produksi, tetapi menggunakan mekanisme seperti `docker debug` atau ephemeral container. Jadi ukuran runtime yang kecil dan permukaan runtime yang minimal dibayar dengan pengalaman debugging yang lebih terbatas.

Setelah image API dapat dijalankan dengan benar, saya mempelajari bagaimana Docker Compose menghubungkan API dengan PostgreSQL dan Redis. Pada stack core yang sudah diverifikasi, ketiga service tersebut dapat berjalan dalam keadaan `healthy`. Compose membuat network internal sehingga service dapat saling menemukan menggunakan nama service. Karena itu, API tidak perlu mengetahui IP address container PostgreSQL atau Redis secara statis. Nama seperti `postgres` dan `redis` dapat di-resolve melalui DNS internal Compose, dan hal tersebut sudah diuji menggunakan `getent hosts` dari network Compose.

Saya juga memahami bahwa container yang sudah dibuat atau berstatus running belum tentu berarti aplikasinya siap menerima koneksi. Karena itu dependency API terhadap PostgreSQL dan Redis menggunakan `depends_on` dengan `condition: service_healthy`. Dengan kondisi tersebut, Compose tidak hanya menunggu container dependency dibuat, tetapi menunggu healthcheck PostgreSQL dan Redis menyatakan service siap. Hal ini penting khususnya untuk database karena proses database dapat membutuhkan waktu setelah container dimulai sebelum benar-benar siap menerima koneksi.

Untuk penyimpanan PostgreSQL, saya menggunakan named volume `postgres-data`. Named volume mempunyai lifecycle yang terpisah dari container sehingga data tidak hilang hanya karena container dihentikan atau dibuat ulang. Persistence ini dibuktikan dengan memasukkan data berupa baris `id=42`, menjalankan lifecycle Compose yang menghentikan container, lalu memastikan data tersebut masih tersedia setelah service dijalankan kembali. Dari sini saya memahami perbedaan antara container sebagai unit runtime yang dapat diganti dengan data persistent yang perlu bertahan lebih lama.

Pendekatan tersebut berbeda dengan source API pada development environment. Untuk development, source code menggunakan bind mount dari filesystem host ke container. Tujuannya bukan persistence database, tetapi supaya perubahan file yang saya lakukan pada host langsung terlihat di dalam container. Air kemudian memantau perubahan tersebut dan melakukan build serta menjalankan ulang aplikasi secara otomatis. Versi Air yang dipin adalah `v1.61.7`, dan command build sementara yang digunakan adalah `go build -o /tmp/air/api ./cmd/api`. Hot reload sudah diuji dengan melihat Air mendeteksi perubahan source kemudian melakukan build dan run ulang.

Saya juga mempelajari resource limit container. Pada konfigurasi Compose saat ini, API dibatasi `128m`, PostgreSQL `512m`, dan Redis `128m`. Docker menerapkan batas tersebut melalui mekanisme resource isolation yang pada Linux berhubungan dengan cgroup. Ketika sebuah process menggunakan memori melebihi batas yang diberikan dan kondisi tidak dapat dipertahankan, kernel dapat menghentikan process tersebut. Saya melakukan demonstrasi terpisah menggunakan container Alpine dengan limit `32MiB`, dan hasil inspeksinya menunjukkan `OOMKilled=true` serta exit code `137`.

Dari eksperimen OOM tersebut saya memahami bahwa exit code `137` berkaitan dengan process yang dihentikan menggunakan signal `SIGKILL`, yang secara konvensi menghasilkan nilai `128 + 9`. Dalam kasus demonstrasi resource limit, Docker juga mencatat bahwa container mengalami OOM kill. Namun saya juga memahami batas evidence yang saya miliki: demonstrasi OOM dilakukan pada limit 32MiB, sedangkan konfigurasi Compose menggunakan 128MiB, 512MiB, dan 128MiB. DoD yang secara literal menyebut demonstrasi container 256MB karena itu belum saya tandai selesai. Saya tidak boleh mengubah hasil eksperimen menjadi klaim 256MB jika angka tersebut memang tidak pernah diuji.

Selain runtime lokal, saya juga mempelajari multi-platform image. Docker Buildx digunakan untuk membangun image untuk `linux/amd64` dan `linux/arm64`. Image tersebut kemudian dipublikasikan ke GitHub Container Registry, dan manifest GHCR telah diperiksa serta menunjukkan kedua platform tersebut. Dari sini saya memahami bahwa satu tag image dapat menunjuk ke manifest yang memiliki variant untuk lebih dari satu arsitektur sehingga registry dapat menyediakan image yang sesuai dengan platform target.

Namun keberadaan image `linux/arm64` dalam manifest tidak sama dengan membuktikan bahwa image tersebut sudah benar-benar dijalankan pada runtime ARM64. Laptop yang saya gunakan adalah amd64, sehingga evidence saya saat ini membuktikan bahwa image arm64 dapat dibangun dan dipublikasikan, tetapi belum membuktikan perilaku runtime-nya pada host ARM64. Untuk membuat klaim bahwa runtime arm64 benar-benar sehat, saya masih membutuhkan host arm64 atau emulator yang diizinkan kemudian menjalankan healthcheck dan memverifikasi arsitektur runtime.

Saya juga mempelajari risiko command maintenance Docker. Target `make prune` sebelumnya menggunakan `docker system prune -af --volumes`. Opsi `--volumes` berbahaya karena dapat memperluas penghapusan sampai ke volume yang berisi data database. Karena itu target tersebut diubah agar `make prune` rutin tidak menghapus volume. Tindakan yang memang dapat menghapus volume dipisahkan menjadi `make prune-hard` dan membutuhkan konfirmasi eksplisit berupa teks `DESTROY`. Dari perubahan ini saya memahami bahwa command destructive sebaiknya mempunyai scope yang jelas, nama yang jelas, dan friction tambahan agar tidak mudah dijalankan tanpa sengaja.

Pada minggu ini saya juga mengganti Docker Desktop dengan Docker Engine karena environment development saya berada pada laptop dengan RAM 8GB. Namun saya tidak mengklaim angka penghematan RAM tertentu. Percobaan menggunakan `free -h` di WSL tidak dapat digunakan untuk membandingkan konsumsi seluruh Docker Desktop dan Docker Engine pada host Windows, karena command tersebut hanya mengamati memori dari sudut pandang distro WSL. Jika saya ingin menyatakan bahwa Docker Engine menghemat sejumlah RAM tertentu, pengukuran harus dilakukan pada layer host yang sama menggunakan metode yang konsisten sebelum dan sesudah perubahan.

Hal lain yang saya pelajari adalah pentingnya menggunakan alat ukur yang benar untuk pertanyaan yang sedang dijawab. Minggu ini beberapa kesalahan observasi muncul karena command menghasilkan output yang terlihat relevan tetapi sebenarnya mengukur objek yang berbeda. `grep fmt.Println` misalnya dapat menemukan teks di komentar dan bukan hanya kode executable. `free -h` di WSL tidak membuktikan konsumsi memori seluruh host Windows. Ukuran image tidak membuktikan efektivitas `.dockerignore`, karena yang harus diperiksa adalah transfer build context. Selain itu, ekspresi `$(...)` pada Make dapat diproses oleh Make sebelum sampai ke shell apabila tanda `$` tidak di-escape dengan benar. Dari pola tersebut saya memahami bahwa sebelum menggunakan sebuah command sebagai evidence, saya harus menentukan apa objek yang ingin diukur, pada layer mana pengukuran dilakukan, dan output seperti apa yang benar-benar dapat membuktikan klaim tersebut.

Test suite API juga saya jalankan kembali dari terminal manusia menggunakan `make test`, yang menjalankan `go test -race -count=1 ./...`. Test yang tersedia pada package `internal/config`, `internal/healthcheck`, dan `internal/http` lulus, sedangkan `cmd/api` melaporkan `[no test files]`, yang bukan merupakan kegagalan. Tidak muncul laporan data race selama eksekusi tersebut. Saya memahami bahwa race detector hanya dapat menemukan race pada jalur kode yang benar-benar dieksekusi selama test, sehingga hasil tersebut bukan jaminan bahwa semua kemungkinan race di seluruh aplikasi pasti tidak ada.

Walaupun sebagian besar fondasi Docker dan Compose sudah tersedia, saya juga memahami batas dari pekerjaan Minggu 2 ini. Stack core yang sudah diverifikasi saat ini terdiri dari API, PostgreSQL, dan Redis. Service web belum berada dalam profile core, sehingga komunikasi web ke API melalui nama service belum mempunyai evidence dan tidak boleh saya klaim sudah terbukti. Profile `storage` dan `obs` juga belum mempunyai implementasi service dan direncanakan untuk scope berikutnya. Runtime arm64 masih membutuhkan pengujian runtime tersendiri, dan penghematan RAM akibat migrasi Docker runtime belum mempunyai angka pengukuran yang valid.

Dari seluruh latihan Minggu 2, saya memahami bahwa Docker bukan hanya cara membungkus aplikasi menjadi image. Dockerfile menentukan bagaimana artefak dibangun dan apa yang akhirnya masuk ke runtime. Distroless membantu membuat runtime kecil dan minimal, tetapi membawa konsekuensi terhadap debugging dan healthcheck. Compose kemudian mengatur hubungan antar-service, DNS internal, dependency berdasarkan health, volume persistent, development bind mount, dan resource limit. Buildx dan registry memperluas image yang sama agar dapat didistribusikan untuk lebih dari satu arsitektur.

Kesimpulan saya dari Minggu 2 adalah bahwa container yang dapat `build` dan `run` saja belum cukup untuk disebut siap. Saya harus dapat membuktikan image kecil dan berjalan non-root, healthcheck benar-benar bekerja pada runtime aktual, service dapat menemukan dependency melalui networking Compose, data database bertahan melewati lifecycle container, resource limit benar-benar diterapkan, development hot reload bekerja, dan image multi-platform benar-benar tersedia di registry. Yang sama pentingnya, saya harus mampu membedakan antara hal yang sudah dibuktikan, hal yang baru dapat diinferensikan, dan hal yang memang belum diuji. Tujuan latihan ini bukan sekadar membuat saya hafal command Docker, tetapi membuat saya mampu menjelaskan alasan setiap keputusan, trade-off yang dipilih, failure mode yang mungkin terjadi, serta evidence apa yang benar-benar mendukung setiap klaim.
